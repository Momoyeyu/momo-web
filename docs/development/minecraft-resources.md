# Minecraft resources and remaining account prerequisite

The Fabric component builds with Java 21 and Gradle 8.10.2 through `scripts/build-minecraft-component.py --gradle /qualified/gradle --cache /isolated/cache`. The script verifies the Gradle version, builds with an isolated cache, and reports the output SHA256. Generated jars remain ignored.

`backend/app/services/minecraft_resources.py` qualifies a maintainer-prepared local resource closure and copies it into a new, dedicated instance. A schemaVersion 1 manifest contains exact `pins` (Minecraft 1.21.1, loader 0.16.14, fabricApi 0.116.4+1.21.1, java 21), `files` entries with relative path/SHA256, `classpath` jar paths, and `mainClass: net.fabricmc.loader.impl.launch.knot.KnotClient`. Companion jar must be present. Existing instances are never overwritten. This manifest is trusted release input, not user/model-supplied code; hashes verify integrity, not safety or licensing. Qualification verifies the prepared closure; the official metadata resolver is described below. A product release still needs graphical startup and platform-specific acceptance.

Microsoft device code flow requires a registered public client application. The product maintainer must register momo, support the intended personal Microsoft accounts, and enable the appropriate public client flow. See [Microsoft flow documentation](https://learn.microsoft.com/en-us/entra/identity-platform/msal-authentication-flows). A desktop public client does not keep a client secret. A registration alone is not evidence of Minecraft entitlement access: verify Xbox and Minecraft token exchange, Java ownership/profile, and refresh/revocation with a consenting test account before enabling launch.

[Prismarine Auth's API](https://github.com/PrismarineJS/prismarine-auth/blob/master/docs/API.md) supports an owned client ID via `authTitle` and `flow: 'msal'`. Its documented `live` flow and exported official app IDs are not an acceptable shortcut for momo. The implementation uses direct bounded identity requests rather than this library; no live login requests were made. Credentials stay in private storage and excluded from logs, backups, UI status and command lines; the bridge token should be generated internally per instance rather than entered by users.

## Implemented continuation (2026-11-05)

`minecraft_auth.MinecraftAuth` now implements the owned-client device-code flow, bounded polling/expiry/slow-down, refresh, Xbox/XSTS exchange, Minecraft Java entitlement/profile validation, and atomic mode-0600 refresh-token storage. Only public code/verification URL/profile are returned by the public auth methods; `session()` is private launcher input. No live identity calls have been made. The managed API stores credentials outside ordinary state/backup exports. Startup cancellation does not wait for slow identity requests; permission checks run again before launch.

`ManagedMinecraftInstance.launch(session, port)` now launches a qualified Java21 client when supplied a validated nonexpired session; the earlier unavailable-only launch description is superseded. It generates the bridge token internally, uses a mode-0600 Java argument file so access/bridge tokens do not appear in OS command arguments or environment, and removes that file on process exit. A supervisor owns its direct Java child and the argument file. Backend crash/SIGKILL closes its unique lifetime pipe, triggering bounded terminate/kill/wait and cleanup; no PID scan or unrelated-process signalling is used. Launch opens the dedicated client, without joining a server automatically.

`scripts/prepare-minecraft-resources.py --destination NEW_DIR --mod BUILT_JAR` resolves the pinned official Minecraft/Fabric metadata during resource preparation, validates official SHA1 download checksums, and writes SHA256 entries for the assembled release closure. It downloads libraries/assets/native archives and the Fabric API. This is a release-preparation tool, never a runtime download path. Actual preparation is documented below; graphical client startup still needs acceptance. Isolated tests cover private launch-argument handling, blocked-refresh cancellation, readiness cancellation and a real isolated parent SIGKILL cleanup. No live account/server acceptance is claimed.

## Actual preparation verification (2026-11-05)

Official closure preparation and subsequent qualification succeeded on macOS arm64: 3,963 files, 72 classpath jars, 3,888 asset objects, 924,738,155 bytes. Every downloaded object matched its official SHA1; the assembled manifest's SHA256 entries were rechecked. Fabric KnotClient main class exists in the qualified classpath. The latest original mod (authenticated nonmutating `ping` readiness command included) rebuilt successfully and matched the prepared copy, SHA256 `d1621e8042d65ba88ef818ef50c60a4e4ebc1765be930357e0313a940d7085a2`.

Preparation now uses six bounded asset-download workers, four bounded retries, and a persistent digest-verified cache. A final-manifest progress-variable shadowing error was caught during actual preparation, fixed, covered by a complete mocked preparation test, and the rerun reused verified cached artifacts. Four resolver tests pass. The local ignored output is `.workbuddy/minecraft-resources`; it is development evidence, not committed/bundled user resources. Java21 selection prefers `/usr/libexec/java_home -v 21` on macOS; launch requires a matching platform/architecture manifest. Argument-file cleanup belongs to the per-launch supervisor; a replacement host does not delete another live launch’s file.

This verifies resource acquisition and integrity, not an actual Minecraft graphical launch, account login, server join, or safe follow behavior. Those live acceptance steps remain unperformed.
